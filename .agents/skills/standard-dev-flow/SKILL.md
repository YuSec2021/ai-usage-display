# 标准开发流程

在完成下述准备门禁前，不得修改实施产物；门禁完成前允许创建 Issue 草稿和必要的准备文档。每项变更必须从一个 Issue 开始，并且只能使用一个工作分支。根据 Issue 类型完成对应准备工作；对于明确不需要模块设计的类型，不得强制要求模块设计。

## 类型与分支规则

| `type/*` | 准备要求 | 工作分支 |
|---|---|---|
| `type/feature` | 必须提供模块设计，哪怕只有半页 | `feature/<板块号>-<短描述>` |
| `type/bug` | 不需要模块设计；必须提供四行根因说明 | `bug-<issue号>` |
| `type/chore` | 不需要模块设计 | `chore/<issue号>-<短描述>` |
| `type/docs` | 不需要模块设计 | `docs/<issue号>-<短描述>` |
| `type/spike` | 不需要模块设计；产出物就是文档 | `spike/<issue号>-<短描述>` |
| `type/refactor` | 必须提供模块设计 | `feature/<板块号>-<短描述>` |

长期存在的环境分支不是工作分支，不纳入一对一映射。

## 必须执行的顺序

1. 提出设计前，阅读适用的仓库说明和架构决策。
2. 确保先有 Issue，再产生其他实施产物：
   - 已有 Issue 链接或 ID 时，使用现有 Issue。
   - 已获授权且 Issue 管理系统可用时，使用 [assets/issue.md](assets/issue.md) 创建 Issue。
   - 否则，使用该模板生成完整的 Issue 草稿。获得代码实施权限不等于获得修改外部 Issue 管理系统的权限。
3. 填写 Issue 类型、唯一工作分支、背景、目标、范围、初始验收标准和状态。不得虚构 Issue 号，也不得声称存在未经核实的分支关联。
4. 执行对应类型的门禁：
   - `type/feature` 和 `type/refactor`：使用 [assets/module-design.md](assets/module-design.md) 创建设计文档，并完成其中的复用声明。若仓库没有既定约定，则使用 `docs/design/<issue-id-or-task-slug>.md`。
   - `type/bug`：填写现象、定位到具体代码位置的根因、影响面，以及防止复发的回归检查。
   - `type/chore` 和 `type/docs`：记录 `N/A — 当前类型不需要设计`。
   - `type/spike`：明确调研将产出的文档及其需要回答的决策问题。
5. 创建模块设计时，先在仓库中搜索相关能力并检查既有实现和调用方。在复用声明中如实回答：仓库是否已有该能力、搜过什么关键词、看过哪些既有实现、为什么不能复用。可以完全复用时，最后一项填写 `N/A — 将直接复用 <既有实现>`，不得虚构不能复用的理由。
6. 在 Issue 或必需的设计文档中拆解受影响模块。明确具体路径或组件、契约与数据变更、调用方、验证门禁和发布注意事项。
7. 根据类型，将设计、根因说明或调研产出，以及模块拆解、风险和验证计划回填到 Issue。
8. 确认该 Issue 没有其他工作分支，并且目标分支未分配给其他 Issue。在 Issue 中记录最终分支名。
9. 核验准备门禁。只有通过后才能开始实施。
10. 实施期间，持续更新 Issue 状态和验收标准。范围或设计发生变化时，必须先更新准备产物和模块拆解，再继续实施。

## 准备门禁

实施变更前必须满足以下所有条件：

- 已有 Issue ID、链接，或有一份可提交到项目 Issue 管理系统的完整草稿。
- 只有一个 `type/*` 值，并且只有一个符合类型映射的工作分支。取得真实 Issue 号前，本地草稿可以使用映射中的占位符，但不得根据占位符创建分支。
- `type/feature` 和 `type/refactor` 已落地模块设计，并基于真实仓库检索完整填写复用声明；`type/bug` 已填写四行根因说明；`type/spike` 已明确产出文档；或 `type/chore` 和 `type/docs` 已明确标记无需设计。
- 复用声明明确记录仓库是否已有该能力、搜索关键词、看过的既有实现及路径，以及不能复用的具体原因；可以完全复用时，明确记录将直接复用的实现。
- 已完成包含受影响代码区域的模块拆解。
- 已填写验收标准，以及具体的测试、评测、构建或审查计划。
- 已满足适用的仓库特定要求，例如 ADR 审查、埋点、迁移、安全性、无障碍、发布或回滚要求。

如果任务仅要求准备计划，通过门禁后停止，并将产物交给用户。如果任务还要求实施，通过门禁后直接继续；只有仍缺少关键决策或新的授权时才请求确认。

## 模块拆解规则

- 根据类型对应的准备工作和仓库现有边界划分模块；不得只为增加列表长度而拆分工作。
- 提出新的辅助函数、抽象、依赖、配置或服务前，先追踪调用方并复用现有代码。
- 小改动应保持精简：一个受影响模块足以覆盖全部工作时，就是有效拆解。
- 保留现有的架构、安全、质量、测试、评测、可观测性、无障碍、埋点和发布门禁。项目要求 ADR 时，按类型执行的准备工作不能替代 ADR。

## 产出物

复制并填写模板；产出完成后删除其中的指导性注释：

- `type/feature` 和 `type/refactor` 使用 [assets/module-design.md](assets/module-design.md) 创建设计文档，并完整填写复用声明。
- Issue 正文或本地草稿使用 [assets/issue.md](assets/issue.md)。

对于确实不适用的必填章节，使用 `N/A — <原因>`。不得静默删除与风险相关的章节。
